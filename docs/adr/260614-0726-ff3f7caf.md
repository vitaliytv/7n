## PULL — отримати зміни з сервера

### Класичний `git pull`
1. Завантажує зміни з origin (`git fetch`)
2. Намагається злити (`git merge`) або перебазувати (`git rebase`) — залежно від налаштувань
3. Якщо є конфлікт — зупиняється посередині з маркерами `<<<<<<` у файлах
4. Розробник мусить вручну редагувати кожен конфліктний файл, потім `git add` + `git merge --continue`
5. Незакомічені локальні зміни можуть заважати — git або відмовляє, або вимагає спочатку зробити `git stash`
6. Після успіху — новий merge-коміт (або лінійна історія при rebase)

### `npx @7n/n pull`
1. Завантажує зміни з origin (`git fetch`)
2. **Якщо немає розбіжності (fast-forward)** — просто переміщує HEAD вперед, нічого зайвого
3. **Якщо є розбіжність (гілки розійшлися)**:
- Спочатку зберігає весь поточний стан у безпечне місце (`git stash create` — коміти + staged + unstaged)
- Переводить HEAD точно на версію origin (`git reset --hard origin`)
- Рахує **дельту** — що відрізняється між точкою розгалуження і твоїм локальним станом
- Накладає лише цю дельту зверху на оновлений origin
4. **Конфлікти вирішуються автоматично в 4 рівні** (від дешевого до дорогого):
- Рівень 0: `git apply` — простий патч без контексту конфлікту
- Рівень 1: `git merge-file --diff3` — класичне 3-стороннє злиття
- Рівень 2: Mergiraf — розумне AST-злиття (розуміє структуру коду)
- Рівень 3: LLM-агент — лише для файлів, де ще залишилися маркери конфліктів
5. Результат: HEAD = чиста версія origin, твої локальні зміни лежать зверху незакоміченими (щоб ти сам переглянув і закомітив)
6. У будь-який момент — відкат одною командою (надрукована на екрані)

## PUSH — відправити зміни на сервер

### Класичний `git push`
1. Перевіряє, чи є нові коміти локально
2. Якщо origin "попереду" (хтось інший вже запушив) — відмовляє з помилкою
3. Розробник мусить сам зробити `git pull` (з можливими конфліктами), потім повторити `git push`
4. Усі локальні коміти (скільки б їх не було) йдуть на сервер як є — з їхніми повідомленнями, навіть якщо це "wip", "fix", "aaa"
5. Commit message — завжди написаний вручну або взятий як є

### `npx @7n/n push`
1. Завантажує актуальний стан origin (`git fetch`)
2. **Якщо origin "попереду"** — автоматично підтягує нові коміти через те саме delta-ядро (без зупинок і ручного merge)
3. **Squash усього в 1 коміт**: додає ВСЕ (`git add -A`), скидає на рівень origin (`git reset --soft`), щоб усі локальні зміни стали одним коміт-кандидатом
4. **Генерує commit message** (два шляхи):
- **Шлях A (без LLM, миттєво)**: якщо в папці `.changes/` є markdown-файли з описом змін — читає їх, визначає тип зміни (Added/Fixed/Changed/Removed), mapує на emoji і тип (`✨feat`, `🐛fix`, тощо), будує повідомлення детерміновано
- **Шлях B (LLM-фолбек)**: якщо change-файлів немає — збирає git diff (без шуму: без lock-файлів, без build-артефактів), послідовно пробує `pi → claude → cursor` як LLM-агентів
5. Робить коміт (`git commit --no-verify`) з готовим message
6. Пушить на origin (fast-forward або `-u` для нової гілки)
