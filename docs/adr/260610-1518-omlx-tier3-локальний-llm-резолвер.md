# Заміна cloud-агентів (pi/claude/cursor) на локальний omlx у Tier-3 резолві конфліктів

**Status:** Accepted
**Date:** 2026-06-10

## Context and Problem Statement

Ядро `_n7merge_delta` (`npm/merge.js`) делегувало нерозв'язані конфліктні маркери ланцюжку `pi -p → claude -p → cursor-agent`. Агент `pi` повертав `<eos>` із exit 0, не виконував жодних edit-викликів і лишав маркери у файлах без помилки — клас помилок неможливо виявити з боку shell. Паралельно reverse-delta pull потребував детермінованого резолвера для конфліктів при `_n7merge_delta "origin/<branch>" "$backup_ref"`.

## Considered Options

* Залишити ланцюг `pi → claude → cursor` і виправити лише баг `<eos>`
* Замінити тільки `pi` на omlx, зберігши cloud-агентів як фолбек
* Повна заміна ланцюга: omlx-only, без cloud-фолбеку
* Reverse-delta з обертанням ролей у `_n7merge_delta`

## Decision Outcome

Chosen option: "Повна заміна ланцюга: omlx-only", because керування клієнтським generate-validate циклом у JS (а не інструментальний tool-loop агента) усуває клас помилок типу `<eos>`: аплай і валідація детерміновані на боці JS, модель лише генерує текст; cloud-агентів видаляють свідомо — деградація при недоступному omlx = маркери лишаються + чітка помилка (безпечно прикрито `git stash create`-бекапом від reverse-delta pull).

### Consequences

* Good, because JS-резолвер (`npm/omlx.mjs`, `npm/omlx-resolve.mjs`) unit-тестований через fake-fetch; 90/90 тестів зелені.
* Good, because modify-beats-delete вирішує `delete/modify` детерміновано у Tier 1 без LLM; банер `💀→✅ ВРЯТОВАНО ВІД ВИДАЛЕННЯ` з людськими підписами сторін (`ours_label`/`src_label`).
* Good, because live e2e на `gemma-4-e4b-it-OptiQ-4bit` розв'язав реальний конфлікт: pure-add `host` збережено, `port` замінено, маркерів нема, Tier 3 omlx активовано.
* Bad, because gemma-4-e4b (4B) слабша за cloud-агентів на семантичному мерджі; компенсація: валідатори V1–V7 з таргетованим ретраєм (N=3 дефолт), strict V6 увімкнено.
* Bad, because без cloud-фолбеку при недоступному omlx (HTTP 507 — memory ceiling; сервер лежить) маркери лишаються на ручний резолв без авто-старту.

## More Information

Змінені файли: `npm/merge.js`, `npm/pull.js`, `npm/omlx.mjs` (новий), `npm/omlx-resolve.mjs` (новий), `npm/tests/omlx.test.mjs` (новий), `npm/tests/merge.test.mjs`, `npm/tests/pull.test.mjs`, `npm/tests/push.test.mjs`, `npm/package.json`.

Конфігурація:
- Endpoint: `~/.omlx/settings.json` → `server.host/port`; env `N7MERGE_OMLX_URL`
- Модель: `is_default` з `~/.omlx/model_settings.json`; env `N7MERGE_OMLX_MODEL`
- Ключ: `auth.api_key` (дефолт `omlx-local-test-key`); env `N7MERGE_OMLX_KEY`
- Температура форсована 0 (server-default 1.0 руйнує детермінізм)
- Ретраї: `N7MERGE_OMLX_RETRIES` (дефолт 3); strict V6: `N7MERGE_OMLX_STRICT` (дефолт увімкнено)
- `RESOLVER_PATH`: `fileURLToPath(new URL('omlx-resolve.mjs', import.meta.url))` інжектується у `runZsh` через `env`

Транспорт відповіді: sentinel-блок `<<<N7-RESOLVED` / `N7-RESOLVED>>>`. JSON зі структурою відхилено після тестування: e4b плутає екранування переносів у JSON-payload, що ламає `JSON.parse`.

Валідатори (unit-тестовані чисті функції):
- V1: відсутність маркерів `<<<<<<<` / `|||||||` / `=======` / `>>>>>>>` у результаті
- V2: непорожній результат (крім explicit-empty: обидва боки порожні)
- V3: відсутність прози поза sentinel, code-fence та преамбул
- V4: кожен рядок результату існує в `ours ∪ base ∪ theirs` (trim; anti-hallucination; толерує комбінації)
- V5: ≥1 pure-add з кожної сторони вцілів, якщо обидві мають pure-adds
- V6 (strict, дефолт): всі pure-adds вцілюють; `similarEdit()` — загальний префікс ≥50% і ≥3 символи
- V7: length-guard — рядків ≥ max(meaningful(ours), meaningful(theirs))

Критичний баг: `.js`-розширення резолвера спричиняло `ERR_INVALID_PACKAGE_CONFIG` коли `package.json` у конфлікті (Node читає найближчий `package.json` для визначення ESM/CJS). Виправлено: `omlx.js → omlx.mjs`, `omlx-resolve.js → omlx-resolve.mjs` — ESM визначається автоматично, `package.json` не читається під час старту.

Health-check: `GET /v1/models` перед роботою; при недоступному omlx — exit 1 без авто-старту. Warm-latency gemma-4-e4b: ~0.85 с/хунк (cold: ~32 с). Гранулярність: per-hunk (diff3-парсинг у JS).

## Update 2026-06-10 (еволюція формату відповіді та деталі валідаторів)

**response_format: json_schema → sentinel-блоки**

Під час дизайну спочатку обрано `response_format: json_schema` (поле `resolved: string`): тест підтвердив, що gemma-4-e4b коректно повертає валідний JSON без преамбул, unique-рядки обох сторін збережено. Однак у пізнішому тестуванні виявлено плутанину з екрануванням переносів у JSON-payload — e4b видавав подвійний escape замість одинарного, що ламало `JSON.parse`. Остаточно обрано sentinel-блок `<<<N7-RESOLVED` / `N7-RESOLVED>>>` як надійніший транспорт для малих моделей.

**Деталі валідаторів**

- V4: membership-тест trim-рядків у `ours ∪ base ∪ theirs`; толерує комбінації рядків (не вимагає ідентичних)
- V5: перевіряється лише якщо обидві сторони мають pure-adds
- V6: `similarEdit()` — загальний префікс ≥50% і ≥3 символи відрізняє same-line-правку від окремого доповнення
- V7: length-guard на рівні `max(meaningful(ours), meaningful(theirs))`
- Two-phase підхід для складних хунків збережено у фінальній реалізації

## Update 2026-06-10 (live e2e та .mjs баг)

**Live e2e підтвердження**

Повний pull-флоу з реальним конфліктом: pure-add `host = "0.0.0.0"` збережено, `port = 3000` замінено, маркерів нема, Tier 3 omlx активовано. При перевищенні memory ceiling omlx повертає HTTP 507 — резолвер акуратно репортує `omlx HTTP 507: memory ceiling` без краша.

**Критичний баг та виправлення (підтвердження)**

Проблема: `.js`-розширення резолвера → `ERR_INVALID_PACKAGE_CONFIG` коли `package.json` у конфлікті. Node читає найближчий `package.json` під час старту для визначення CJS vs ESM; невалідний JSON → crash до запуску резолвера. Виправлено перейменуванням на `.mjs`. Ізольований тест: `.mjs` стартує нормально; `.js`-контроль — падає. Результат: 90/90 тестів зелені, lint чисто.
