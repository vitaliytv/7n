## ADR omlx як єдиний Tier-3 LLM-резолвер конфліктів мерджу

## Context and Problem Statement
Попередній ланцюг cloud-агентів (`pi → claude → cursor`) для Tier-3 резолву конфліктів мерджу мав ваду: агент міг повернути `<eos>` без виклику `edit`-інструмента, файл лишався з маркерами при exit 0. Необхідна детермінована заміна з клієнтським контролем аплаю.

## Considered Options
* Заміна LLM-тіру на локальний omlx (OpenAI-сумісний HTTP, MLX-моделі) з клієнтським generate-validate циклом у JS
* Інші варіанти в transcript не обговорювалися.

## Decision Outcome
Chosen option: "Заміна лише LLM-тіру на omlx-only (скоуп A)", because зберігає детерміновані Tier 0–2 (`git apply → merge-file → mergiraf`) в zsh без змін; лише Tier-3 (`_n7merge_resolve_with_agent`) замінюється на `node omlx-resolve.mjs <files>`, де JS контролює аплай і валідацію незалежно від моделі.

### Consequences
* Good, because transcript фіксує очікувану користь: усунуто баг `<eos>` — аплай детермінований у JS, модель лише генерує текст; live e2e підтвердив успішний резолв (e2b, ~1.5 GB) на Mac 16 GB з стелею 12 GB.
* Bad, because e2b (2B) слабша за cloud-агентів на складних мерджах — `package.json`-конфлікт навіть після 3 ретраїв з V8 не вдалося зрезолвити автоматично (залишились маркери); поведінка залежить від доступності локального сервера omlx.
