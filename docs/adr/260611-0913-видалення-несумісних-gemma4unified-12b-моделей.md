## ADR Видалення несумісних gemma4_unified 12B моделей

## Context and Problem Statement
В omlx 0.4.3 з mlx-lm 0.31.3 (release) моделі `mlx-community/gemma-4-12B-it-OptiQ-4bit` і `mlx-community/gemma-4-12B-it-qat-4bit` завантажувались із помилкою `ValueError: Missing 711 parameters` — обидві використовують архітектуру `Gemma4UnifiedForConditionalGeneration` (`model_type: gemma4_unified`), яка не підтримувалась у тодішньому завантажувачі.

## Considered Options
* Залишити моделі й чекати upstream-фіксу
* Видалити через `DELETE /admin/api/hf/models/{model_id}` і звільнити місце

## Decision Outcome
Chosen option: "Видалити через API", because обидва завантажувачі (`mlx_lm.load` HEAD і `mlx_vlm.load` 0.6.2) повертали ту саму помилку `Missing 711 parameters`; подальше тестування моделей без робочого рантайму неможливе.

### Consequences
* Good, because transcript фіксує очікувану користь: звільнено ~8.7 GB (`gemma-4-12B-it-OptiQ-4bit` — 4.6 GB partial, `gemma-4-12B-it-qat-4bit` — 4.1 GB partial).
* Bad, because 12B-клас Gemma 4 стає недоступним до появи повноцінної підтримки `gemma4_unified` в omlx/mlx-vlm.

## More Information
- Команди: `curl -X DELETE http://127.0.0.1:8000/admin/api/hf/models/gemma-4-12B-it-OptiQ-4bit`, аналогічно для `gemma-4-12B-it-qat-4bit`
- Корінь проблеми: commit `8239c72` у mlx-lm (2026-06-05) додав маппінг `gemma4_unified → gemma4` у `MODEL_REMAPPING` і `sanitize()`, але per-layer mixed-precision quant config у `_quantize()` predicate не відповідає структурі ключів `language_model.model.X.*` — підтримка лише часткова
- 4B-варіант `gemma-4-e4b-it-OptiQ-4bit` працює, бо має `model_type: gemma4` (не unified)

## ADR Оновлення omlx 0.4.3 → 0.4.4.dev1 через .dmg для VLM-підтримки

## Context and Problem Statement
В omlx 0.4.3 `gemma-4-e2b-it-4bit` і `gemma-4-e4b-it-OptiQ-4bit` завантажувались через LLM-fallback (`engine_type: LLM`), а не як VLM — мультимодальні image-запити ігнорувались. mlx-vlm 0.6.2, вбудований у 0.4.3, не підтримував квантизований формат ваг Gemma 4 E4B/E2B.

## Considered Options
* `brew install --HEAD jundot/omlx/omlx` (main = 0.4.4.dev1)
* Встановити .dmg `oMLX-0.4.4.dev1-macos15-sequoia.dmg` з GitHub Releases
* Оновити лише mlx-vlm до HEAD без апгрейду omlx

## Decision Outcome
Chosen option: ".dmg `v0.4.4.dev1`", because користувач обрав .dmg варіант; `pyproject.toml` 0.4.4.dev1 закріплює mlx-vlm за комітом `c9a6743` з коментарем "includes Gemma4 shared-KV/load fixes", що усуває `k_proj/v_proj` несумісність у layers 15-34.

### Consequences
* Good, because transcript фіксує очікувану користь: після встановлення `gemma-4-e4b-it-OptiQ-4bit` завантажилась із `engine_type: vlm` і реально описала тест-зображення (колір, форму, текст "ЖОВТО-СИНІЙ TEST").
* Bad, because ручний апгрейд mlx-lm до HEAD (`0.31.3`), зроблений раніше в сесії, перетертий pinned-версіями з 0.4.4.dev1; обидва пакети однаково `0.31.3` за номером, але різні коміти.

## More Information
- Реліз: `https://github.com/jundot/omlx/releases/tag/v0.4.4.dev1`
- Попереднє видалення brew: `brew services stop omlx && brew uninstall omlx`
- Після встановлення omlx-CLI переїхав на `/opt/homebrew/bin/omlx` (shell-скрипт із bootstrap із `~/Library/Application Support/oMLX/base-path`)
- Дані моделей у `~/.omlx/models/` і `~/.cache/huggingface/hub/` збережені без змін

## ADR Вибір gemma-4-e4b-it-OptiQ-4bit як дефолтної моделі в omlx

## Context and Problem Statement
Після видалення несумісних 12B моделей і перевірки доступних варіантів потрібно було визначити основну робочу модель на 16 GB Mac і виставити її дефолтною (`is_default=true`) та закріпленою в RAM (`pinned=true`).

## Considered Options
* `gemma-4-e4b-it-OptiQ-4bit` (4B, 7.44 GB, engine_type: vlm)
* `rajaschitnis/gemma-4-12b-it-text-only-4bit-mlx` (12B, 10 GB, text-only)
* `Qwen3-4B-Thinking-2507-4bit` (4B, 2.1 GB, text-only)

## Decision Outcome
Chosen option: "`gemma-4-e4b-it-OptiQ-4bit`", because це єдина з доступних моделей, що завантажується як справжній VLM (`engine_type: vlm`) і підтверджено описує зображення; 4/4 функціональних тестів пройшло, швидкість ~28 tps.

### Consequences
* Good, because transcript фіксує очікувану користь: модель завантажена в RAM (7.44 GB), inference підтверджено (`Київ` у 4.11с), VLM-тест із картинкою успішний — text + vision в одному endpoint.
* Bad, because `is_default=true` є полем налаштувань моделі в omlx UI/API, але OpenAI-сумісний `/v1/chat/completions` однаково вимагає явне поле `model` в тілі запиту — автоматичного fallback на рівні API не відбувається.

## More Information
- API для встановлення: `PUT /admin/api/models/gemma-4-e4b-it-OptiQ-4bit/settings` з тілом `{"is_default": true, "is_pinned": true}`
- Force-load: `POST /admin/api/models/gemma-4-e4b-it-OptiQ-4bit/load`
- Фінальний стан: `is_default=True, pinned=True, loaded=True, actual_size_formatted=7.44 GB, engine_type=vlm`
