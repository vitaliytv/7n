## Поточний workflow (без гейту)

```
CI крок 1:  n-cursor release
├── bump version  (0.12.0 → 0.12.1)
├── git commit    (✅ завжди ОК)
└── git push      (❌ може впасти non-ff — але крок ЦЕ ІГНОРУЄ)

CI крок 2:  npm publish          ← запускається безумовно, навіть якщо push не вдався
└── 0.12.1 іде в npm реєстр  ← GIT НЕ ЗНАЄ про цей реліз
```

Тобто `git push` і `npm publish` — послідовні команди в одному скрипті, і якщо перша провалилась, друга все одно виконується. Npm не знає нічого про git — він лише бере `package.json` з раннера і публікує.

## З гейтом

"Гейтувати publish на commit-back" = **перевірити exit code `git push` і зупинити job якщо він ≠ 0**:

```bash
# без гейту (поточна поведінка в n-cursor release):
git push origin main     # rc=1 (non-ff) — але ніхто не перевіряє
npm publish              # виконується попри помилку push

# з гейтом:
git push origin main || { echo "❌ commit-back провалився"; exit 1; }
npm publish              # досягається тільки якщо push ОК
```

Або в yaml:

```yaml
- name: Release (bump + CHANGELOG + tag)
run: bunx n-cursor release
# n-cursor release має завершитись exit 1 якщо git push non-ff

- name: Publish to npm
run: npm publish
# цей крок взагалі не стартує, якщо попередній впав
```

## Що це дає

| Сценарій | Без гейту | З гейтом |
|---|---|---|
| push ОК (звичайний реліз) | ✅ npm + git синхронні | ✅ те саме |
| push non-ff (гонка) | ❌ npm = 0.12.1, git = 0.12.0 | ✅ npm теж не публікується, job = **failure** → видно в CI |

З гейтом "гонка" стає **явно помітним збоєм CI** (червоний workflow), а не тихою розсинхронізацією. Ти побачиш: "commit-back провалився, перезапусти після того як push-гонка вщухне".
