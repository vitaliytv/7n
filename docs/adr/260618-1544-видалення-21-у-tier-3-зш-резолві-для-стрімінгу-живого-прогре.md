## ADR Видалення `2>&1` у Tier-3 зш-резолві для стрімінгу живого прогресу

## Context and Problem Statement
Під час Tier-3 omlx-резолву (`_n7merge_resolve_with_agent`) команда `node "$N7MERGE_RESOLVER" … > "$out" 2>&1` захоплювала і stdout, і stderr у тимчасовий файл. Результат показувався лише після завершення, а весь час роботи (кілька HTTP-запитів до MLX на кожен хунк) користувач бачив один рядок-заголовок і повну тишу — «зависле».

## Considered Options
* Залишити `2>&1`, але дублювати прогрес через `tee` або `mkfifo`.
* Захоплювати лише stdout (`> "$out"`), stdout = machine-readable summary, stderr = живий прогрес у термінал.
* Інші варіанти в transcript не обговорювалися.

## Decision Outcome
Chosen option: "Захоплювати лише stdout (`> "$out"`), stderr успадковує термінал", because це дає живий прогрес без зміни контракту: `$out` лишається чистим per-file підсумком, який zsh-ядро читає далі, а `process.stderr.write` відразу стрімить у термінал.

### Consequences
* Good, because transcript фіксує очікувану користь: прогрес (`📄 [N/M]`, `hunk N/M · спроба K`, причини ретраю) стає видимим у реальному часі, прибираючи ефект «зависло».
* Bad, because transcript не містить підтверджених негативних наслідків.

## More Information
Зміна у `npm/src/merge.js:75`: `node "$N7MERGE_RESOLVER" "${(@f)files}" > "$out"` (без `2>&1`). Тест `npm/tests/merge.test.mjs` перевіряє підрядок `node "$N7MERGE_RESOLVER" "${(@f)files}"` — змінений рядок залишається з ним сумісним.

## ADR Інжектований `onProgress`-колбек у `omlx.mjs` замість прямого `process.stderr`

## Context and Problem Statement
Після фіксу redirect потрібно було додати `process.stderr.write`-виклики всередині `resolveHunk`, `resolveFileText`, `resolveFiles` (`npm/src/omlx.mjs`). Пряме звернення до `process.stderr` у цих функціях зробило б їх нетестовними — вони вже покриті юніт-тестами з DI-ін'єкцією `fetch`/`fs`.

## Considered Options
* Записувати `process.stderr.write(...)` безпосередньо в `resolveHunk` / `resolveFileText` / `resolveFiles`.
* Передавати необов'язковий `onProgress: (event) => void` колбек (default no-op) через `opts` кожного рівня; CLI-ентрі `omlx-resolve.mjs` передає `reportProgress`, що пише у `process.stderr`.
* Інші варіанти в transcript не обговорювалися.

## Decision Outcome
Chosen option: "Необов'язковий `onProgress`-колбек через `opts`", because це зберігає чистоту і тестовність функцій — вони не знають про `process.stderr`, а CLI-шар (`omlx-resolve.mjs`) самостійно вирішує, куди скерувати прогрес. Після змін усі 127 тестів продовжують проходити.

### Consequences
* Good, because transcript фіксує: `bun test` — 127 pass, 0 fail після впровадження; DI-контракт `fetch`/`fs` не зламаний.
* Bad, because transcript не містить підтверджених негативних наслідків.

## More Information
Сигнатури змінено у `npm/src/omlx.mjs`: `resolveHunk(hunk, cfg, fetchFn, extraRule, opts?)`, `resolveFileText(text, cfg, fetchFn, opts?)`, `resolveFiles(files, cfg, deps?, opts?)`. CLI-підключення у `npm/src/omlx-resolve.mjs`: `resolveFiles(files, loadOmlxConfig(), { onProgress: reportProgress })`. Функція `reportProgress` у `omlx-resolve.mjs` пише у `process.stderr`; summary-підсумок лишається у `process.stdout`.
