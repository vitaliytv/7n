## ADR Авто-визначення зачеплених воркспейсів у команді `ch` та видалення прапора `--ws`

## Context and Problem Statement
Команда `npx @7n/n ch` вимагала явного прапора `--ws <шлях>`, щоб визначити, у якому воркспейсі створити change-файл. При виклику з кореня монорепо без `--ws` change-файл завжди потрапляв у кореневий `.changes/`, навіть якщо реальні зміни знаходилися в підпакеті. Користувач запросив автоматичне визначення воркспейсу(ів) за фактичними змінами в git з окремим change-файлом для кожного зачепленого воркспейса.

## Considered Options
* Авто-визначення воркспейсів через `git status --porcelain=v1 -z` + `workspaces` з `package.json`
* Інші варіанти в transcript не обговорювалися.

## Decision Outcome
Chosen option: "Авто-визначення воркспейсів через `git status --porcelain=v1 -z` + `workspaces` з `package.json`", because користувач явно запросив видалити `--ws` і зробити команду «більш розумною» — вона сама дивиться, де є змінені файли, і створює окремий change-файл для кожного зачепленого воркспейса.

### Consequences
* Good, because transcript фіксує очікувану користь: при змінах у двох воркспейсах (`<корінь>` і `npm`) команда автоматично викликала канон двічі з правильними `--ws`, без участі користувача.
* Bad, because transcript не містить підтверджених негативних наслідків.

## More Information
- Файли: `npm/ch.js`, `npm/tests/ch.test.mjs`
- Нові експортовані функції: `parsePorcelainZ`, `resolveWorkspaces`, `groupByWorkspace`, `planChanges`
- `resolveWorkspaces` читає поле `workspaces` кореневого `package.json` (підтримує масив і форму `{packages: [...]}` з простим glob `dir/*`)
- `groupByWorkspace` групує файли за найдовшим збігом префікса
- Канон запускається з `cwd = repoRoot` (результат `git rev-parse --show-toplevel`), тому шляхи коректні незалежно від поточної директорії виклику

## ADR Опційний `--message` з генерацією опису через omlx per-workspace

## Context and Problem Statement
`--message` у `ch` був обов'язковим. Користувач запросив зробити його опційним і автоматично генерувати опис через `omlx`, щоб не вводити текст вручну.

## Considered Options
* Генерація через `omlx` (той самий OpenAI-сумісний MLX-сервер, що і в `merge`/`push`) — окремий промпт на кожен воркспейс із його власним diff
* Інші варіанти в transcript не обговорювалися.

## Decision Outcome
Chosen option: "Генерація через `omlx` per-workspace", because переінжекція того самого `omlxChat`/`loadOmlxConfig`/`ensureModel` з `omlx.mjs` дозволила уникнути нової залежності, а генерація окремого опису з diff кожного воркспейса відповідає вже закладеній логіці «аналіз по воркспейсах окремо».

### Consequences
* Good, because transcript фіксує очікувану користь: вживу omlx згенерував два різних, доречних описи — `"Видалено багато ADR, оновлено ADR про worktree та портабельний виклик n-cursor release"` для кореня і `"Автоматичне визначення воркспейсів та генерація опису змін через omlx"` для `npm`.
* Good, because якщо `--message` задано явно, omlx не викликається — поведінка детермінована й швидка.
* Bad, because transcript не містить підтверджених негативних наслідків.

## More Information
- Файли: `npm/ch.js`, `npm/omlx.mjs`, `npm/tests/ch.test.mjs`
- Нові функції: `workspaceDiffContext(repoRoot, ws, files)` (збирає `git diff --name-status` + `git diff HEAD` + вміст untracked, обрізає до 800 рядків), `buildGenMessages(ws, context)`, `cleanGeneratedMessage(out)`, `defaultGenerator()`

## ADR Пропуск кореневих змін (orphans) у монорепо з підпакетами

## Context and Problem Statement
Після авто-визначення воркспейсів кореневі файли (наприклад, `docs/adr/*.md`), що не належать жодному оголошеному підпакету, потрапляли до кореневого `.changes/`. Але кореневий `.changes/` не обробляється пайплайном `n-cursor release` (згідно з правилом `n-changelog`), тому такий change-файл ніколи не потрапить до `CHANGELOG.md`. Реальний кейс: `efes/shared` з `workspaces: ["npm"]` і лише кореневими ADR-файлами — команда `ch` створила `.changes/260615-0931.md` у корені, але він «мертвий».

## Considered Options
* Пропускати orphan-файли з попередженням у монорепо з підпакетами; root `.` — валідна ціль лише в однопакетному репо (коли `workspaces` порожній або відсутній)
* Інші варіанти в transcript не обговорювалися.

## Decision Outcome
Chosen option: "Пропускати orphan-файли з попередженням у монорепо з підпакетами", because кореневий `.changes/` не опрацьовується ніким; стара поведінка (fallback у корінь) створювала мертві файли.

### Consequences
* Good, because transcript фіксує очікувану користь: при виклику в `efes/shared` із лише кореневими ADR-файлами команда виводить `ℹ️ Поза воркспейсами (CHANGELOG не ведеться, пропускаю): docs/adr/...` і виходить із `exit 0` без створення непотрібного файлу.
* Good, because однопакетні репо (без `workspaces`) не зачеплені — для них `root .` залишається єдиною валідною ціллю.
* Bad, because transcript не містить підтверджених негативних наслідків.

## More Information
- Файли: `npm/ch.js`, `npm/tests/ch.test.mjs`
- Правило, яке пояснює рішення: `.cursor/rules/n-changelog.mdc` — `n-cursor release` агрегує `.changes/` лише в задекларованих підпакетах
- Логіка: `planChanges` повертає `{ groups, orphans }`; перед викликом канону `runCh` логує orphan-шляхи й ігнорує їх
- Тест: `'лише orphan-файли → exit 0, канон не викликається'` (26 тестів, усі зелені)
